# Waflo Mobile — Production v1 Physical-Device E2E Checklist

## Authority and result policy

Run this checklist against `https://api.staging.waflo.app` only after commit `763f2dfccdb24fb9bfa16457f0e49936840e20a1` is deployed and deployment readiness is green. This checklist does not authorize a push/deploy. The exact wire contract is [production-v1-endpoint-catalog.md](production-v1-endpoint-catalog.md).

Result values are `PASS`, `FAIL`, `BLOCKED`, or `NOT_APPLICABLE`. A `BLOCKED` critical case prevents production release; it is not a pass. BCK-001, BCK-002, and BCK-003 are resolved at the audited SHA; approval cases are executable and must not be pre-marked blocked.

Never put a pairing QR, member QR, access/refresh token, private key, signature, approval, customer name, or purchase reference into screenshots, logs, tickets, or analytics. Evidence should contain case ID, device/OS/app build, UTC time, redacted server `requestId`, redacted command UUID, expected/actual code/state, and result.

## Prerequisites

- A release-candidate physical iOS or Android build with staging origin selected at build/config time; no user-editable arbitrary production origin.
- Staging release endpoint independently verified by deployment staff to report the audited SHA; Mobile does not depend on `/ready` at runtime.
- An active staging organization with effective billing (`ACTIVE`, unexpired `TRIALING`, or `GRACE_PERIOD`), a published Loyalty Card, goal between 2 and 30, and one final reward not requiring approval for cases 16–20.
- A second approval-required reward/membership for cases 13–15 and the detailed approval matrix. No raw database fixture is required for the normal supported flow.
- Two active locations: one earning+redemption location and one deliberately restricted location.
- Active Owner/Manager and Staff organization memberships. Provision the target Staff member through supported Merchant `PUT /v1/organizations/:organizationId/members/:memberId/location-assignments/:locationId`, verify it with the matching GET, and retain a second assignment for revocation testing.
- At least two physical Staff devices for concurrency case 10; otherwise mark that case `NOT_APPLICABLE` for a single-device run and do not approve full concurrency sign-off.
- Customer test credentials for same-org, different-org, invalid, Apple Wallet, and Google Wallet. No production customer data.
- A test network proxy or OS network controls capable of offline, response-drop/timeout, and connection-reset simulation without TLS interception in a release build.
- A backend observer with read-only access to command/ledger/audit/outbox/device/session state, or an approved Merchant dashboard view sufficient for the named authoritative check.

## Executable approval E2E matrix

Use distinct test entitlements/commands where a terminal decision would prevent reuse. The first request in every row is the supported signed Mobile redeem; Merchant actions are performed only in Merchant Web. Record public approval IDs only in protected/redacted evidence. No controlled raw database fixture is required for rows A–E or the normal happy path.

| ID | Physical/backend-observer setup and action | Expected result and authoritative check |
|---|---|---|
| A. Required response | Originating Mobile sends approval-required redeem without `managerApprovalPublicId`, using a saved durable UUID key. | `409 MANAGER_APPROVAL_REQUIRED`; details contain public ID, `PENDING`, expiry, `operationType: REDEEM`, and `retryWithSameIdempotencyKey: true`. One reserved command and one request; no redemption. |
| B. Public ID safety | Display only a shortened/redacted reference and retain the full ID with protected pending command state; inspect release logs/crash/analytics. | The exact ID is recoverable by the app for retry but absent from telemetry/screenshots; no internal membership, entitlement, device, Location, or fingerprint data reaches Mobile. |
| C. Merchant list | Manager opens Merchant Web approval queue and finds the public request through GET. | 200 list item matches safe customer/reward/device/Location display context and remains `PENDING`; no Merchant issuance POST is called. |
| D. Manager approve | Manager submits approve with optional reason. | 201 `{ publicId, status:"APPROVED", decidedAt }`; request/decision audits exist and authority was revalidated. |
| E. Exact originating retry | Original device adds only `managerApprovalPublicId`, preserves QR/entitlement/normalized note and the exact original key, and generates a new nonce/time/request ID/signature. | 200 redemption; same reserved command completes. Changing semantic data or key is a FAIL. |
| F. Atomic consume | Observe approval/redemption transaction for row E. | Exactly one conditional `APPROVED → CONSUMED`, redemption, ledger/projection/history/outbox/audit commit; no observable partial state. |
| G. Pending | Before decision, originating device exact-retries with the public ID. | `409 MANAGER_APPROVAL_PENDING`; command/request remains pending and entitlement unchanged. |
| H. Rejected | Manager rejects a fresh request; Mobile exact-retries. | Merchant 201 `REJECTED`; Mobile gets `409 MANAGER_APPROVAL_REJECTED`; reserved command is failed and no redemption occurs. |
| I. Expired | Let a fresh request pass its five-minute expiry, then list/decide/retry. | `410 MANAGER_APPROVAL_EXPIRED`; row is `EXPIRED`, command has the safe terminal failure, no redemption. A new attempt requires a deliberately new key after resolve. |
| J. Wrong device | A second paired device submits the other device's public approval ID and otherwise equivalent public payload. | `409 MANAGER_APPROVAL_MISMATCH`; no state leak or redemption. |
| K. Wrong Location | Use a device/session pinned to another active Location with the captured public ID. | `409 MANAGER_APPROVAL_MISMATCH`; Location authority remains server-derived. |
| L. Wrong membership/entitlement/payload | Change QR membership, entitlement, or normalized note; test same-key semantic change separately from new-key approval reuse. | Same key/different intent gives `OPERATION_IDEMPOTENCY_CONFLICT`; approval presented to a different bound intent gives `MANAGER_APPROVAL_MISMATCH`. No redemption. |
| M. Consumed/reused | After row E succeeds, replay the exact original same-key command, then try the consumed ID under a new command. | Original command returns stored success with `replayed:true`; reuse under another intent returns `MANAGER_APPROVAL_MISMATCH` or `MANAGER_APPROVAL_CONSUMED` according to binding order, never a second redemption. |
| N. Manager permission loss | Approve a fresh request, then suspend/deactivate/remove the approver or otherwise remove current approval authority before Mobile consumption. | Mobile retry gets `409 MANAGER_APPROVAL_APPROVER_INACTIVE`; no consumption/redemption. If authority is lost before decision, Merchant gets `PERMISSION_DENIED`/403. |
| O. Two-manager decision race | Two authorized Managers approve/reject the same pending public ID concurrently; coordinate with backend observer if physical browser timing is impractical. | Exactly one terminal decision; loser receives `MANAGER_APPROVAL_ALREADY_DECIDED` or the observed terminal code. Audit has one winning decision. |
| P. Stale intent | Before approval, invalidate entitlement/requester/device/Location/assignment or redemption policy using supported administration. | Approval attempt returns `409 MANAGER_APPROVAL_STALE` (or lifecycle permission denial at its earlier boundary), row becomes `EXPIRED`, command records safe failure, no redemption. |
| Q. Timeout after success | Let the exact redemption commit but drop its response; preserve the pending command record and restart Mobile if desired. | Originating-device command status returns `COMPLETED`, or exact same-key retry returns `replayed:true`; approval remains consumed once and ledger state is not duplicated. |

Approval-required production release needs every applicable row above to pass. This is a Mobile implementation gate for MOB-004, not BCK-002: the backend HTTP flow is executable at the audited SHA.

## Supported Location-assignment E2E

Before case 3, exercise the Merchant lifecycle without raw database access:

1. GET the target Staff member's assignment list with `devices.view` and confirm the target Location is absent/inactive.
2. PUT `{ "earningAllowed": true, "redemptionAllowed": true }` with `devices.pair` plus Merchant CSRF; expect `changed:true`, active permissions, and a provisioning audit.
3. Repeat the identical PUT; expect `changed:false` and no duplicate audit.
4. Create/complete the normal pairing and verify signed operations use only server-derived organization/Location.
5. Narrow one permission through PUT and prove the corresponding operation is denied while remaining authority can continue; unfinished pairings are canceled.
6. DELETE the assignment; expect `changed:true`, revoked sessions, canceled pairings, expired approvals, audit, and `STAFF_LOCATION_ASSIGNMENT_INVALID` on signed request/refresh.
7. Repeat DELETE; expect `changed:false`. Re-provision with PUT and prove the revoked old session is not restored; complete a new Merchant-initiated pairing.
8. As Manager, attempt a non-Staff target and expect scope denial; prove Staff Mobile never calls GET/PUT/DELETE and has no self-assignment UI or request.

## End-of-run reconciliation

- Resolve every mutated membership and compare `progress`, `goal`, `rewardReady`, `completedCycles`, and `projectionVersion` to Mobile.
- Query each saved command UUID from its originating device; account for every `COMPLETED`/`FAILED` result and safe failure.
- Backend observer verifies contiguous ledger order, exactly-once redemptions/thresholds, audit entries, and no unauthorized/offline mutation.
- Confirm debug logs/crash/analytics evidence contains none of the redaction fields.
- Revoke all staging devices, invalidate test credentials where required, and restore billing/Location/Staff-assignment fixtures through supported Merchant administration endpoints.

## Production smoke scope

After staging passes and production deployment is green, use only approved synthetic production fixtures. Smoke-test origin/build identity, clean pairing, context, one resolve, one idempotent stamp, direct non-approval redemption/reset where specifically authorized, revoke, and logout. Do not run concurrency, deliberate rate/dependency failure, wrong-org customer, or raw database fixture tests against real customer data.
